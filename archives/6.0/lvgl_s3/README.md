# LVGL 核心版固件 (lvgl_s3)

基于 ESP32-S3-N16R8 + ST7789 240x240 + LVGL 8.4.x

## 风格：简约纯黑

- 深黑背景 #000000
- 白色/青色数字文字
- 顶部 NUM/CAPS/SCROLL LED 状态
- 中央大号时钟 (Montserrat 48)
- 日期 + 温湿度 + 击键统计

## 功能（核心优先）

1. **键盘矩阵** - 10x16 完整扫描
2. **USB HID** - 键盘输入 + 媒体键
3. **时间显示** - 时钟 + 日期
4. **温湿度** - SHT31 传感器
5. **简化菜单** - 切换显示模式
6. **HUD 提示** - 分大小两档的操作反馈（见下面「HUD 提示」）
7. **键盘锁定** - 双击静音键锁住，整屏大锁 + 红框告警，Fn+LOGO 解锁
8. **按键速查** - 菜单里一张随时能翻的按键功能表

## 键盘锁定（双击静音键）

把整台键盘"锁住"，锁着的时候**一个字符都不往主机发**，但屏幕要给出
"我收到了，只是被锁着"的明确反馈。

| 动作 | 结果 |
|---|---|
| 双击 C3 上的**静音键** | 锁定 / 解锁（切换） |
| **Fn + LOGO** | 解锁 |
| 锁着时按任意矩阵键 | 吞掉，不发主机；屏幕**红色边框闪一下** |
| 网页 / PC 端 `LOCK:1` / `LOCK:0` | 锁定 / 解锁，回 `LOCKSTATE:0|1` |

- **锁屏长什么样**：240×240 纯黑底，中间一把 132×176 的大锁（白锁体 + 红锁孔），
  下面一行 `YYQ 已锁定`（`已锁定` 是红色）。整块内容垂直居中。
  桌面预览用 `mock_lock.py` 出图（`assets/mock_lock_3x.png`），改排版先改它。
- ⚠ **锁屏上不写"怎么解锁"**：会解锁的人本来就知道，写在屏上等于给旁边的人
  指路。解锁方式只写在菜单的「按键速查」里 —— 那是给机主看的，锁屏是给
  "机主之外的人"看的。
- **锁定状态落 NVS**（键名 `kb_locked`）：重启之后仍然是锁着的。锁的意义就是
  "不让别人打字"，重启就自动解锁的话，拔电重插就能绕过，这锁形同虚设。
- **双击的第一击照常静音**：静音键用得远比"锁定"频繁，为了双击把它延后 350ms
  再执行，手感会明显变钝。代价是双击的副作用是"静音 + 锁定"——两个语义共用
  一个键的必然结果（CPG 双击重启扩展芯片也是同理）。锁着的时候再双击静音键
  同样能解锁，留着这条是为了万一 Fn 键接触不良还有一条自救路。
- **锁着的时候静音键不发 Consumer mute**（锁的意义就是"键盘不控制主机"），
  但**停铃**和**确认通知**照旧——闹钟响着的时候没人能打字，静音键是唯一的
  "停下来"手段。
- **锁着的时候旋钮也不许碰主机**：屏幕亮度和系统音量是 Consumer 页的量，
  锁着拧旋钮等于"锁完顺手把主机音量改了"。所以这两档会闪红框并被忽略。
  但**背光**和**灯效**是键盘自己的，照常能调。
- **锁着的时候 PLAY/NEXT/PREV 连松手都不发**：`ConsumerControl.release()`
  不是空操作，它真往主机发一帧 HID 报告（usage 0）。既然锁了，这一帧也不能有。
- **未锁定时按 Fn + LOGO 什么都不做**（不会切显示风格）。Fn+LOGO 的语义
  就是"解锁"，没锁的时候按它应该没有反应。
- ⚠ **Fn + LOGO 不再是整机重启**。整机重启的入口现在只剩"静音键长按"
  （响铃期间除外，那时它降级成短按静音去停铃）。

### 实现上踩过的三个坑

1. **锁定状态不能塞进 `currentSysMode`**。`currentSysMode` 说的是"当前是哪个
   界面"，锁定说的是"整台键盘不往主机发字"，两者正交——锁着的时候可能在
   菜单里、可能在设置页、可能要息屏，塞进去一换界面锁定就"掉了"。
2. **锁定期间只有锁屏能上屏，统一挡在 `showScreen()` 里**。息屏、倒计时全屏、
   菜单、设置页全都会各自调 `showScreen()`，分散去挡一定漏一处，
   漏一处就表现为"锁着锁着屏幕自己变了"。（`swapAwayIfActive()` 内部是直接
   `lv_scr_load()` 的，但它只在"要删的屏正好是活动屏"时才换，锁屏是活动屏，
   所以它不会把锁屏顶掉。）
3. **锁定判定必须放在"同键连发探测"（`mcpGhostBurstAt`）之前**。那个探测统计
   "同一格连续按下的次数"，超阈值就判 MCP23017 故障。锁着的时候按键是**被吞
   掉**的，但物理上照样按得出来，连按几下就把计数攒到阈值——于是"锁着的时候
   猛按键盘"会把键盘扩展芯片判死，表现成"锁一次键盘就坏了"。
   代价：这一路探测在锁定期间是关着的，MCP23017 真坏了要等解锁才发现
   （另外两路自检——列选自检、空闲态行脚——不在 per-cell 分发里，照常跑）。

### 锁图是怎么进固件的

锁图不是运行时上传的（壁纸那套），而是**编译进 flash** 的 RGB565 数组：

```
assets/lock_src.png  --(gen_lock_img.py)-->  src/lock_img.c  -->  .flash.rodata
```

```bash
/usr/bin/python3 gen_lock_img.py    # 重新生成 src/lock_img.c + src/lock_img.h
```

- 脚本把 MMX 出的图**抠掉背景**（原图背景是暗灰渐变，直接贴到纯黑锁屏上
  会多出一个方块），按亮度做 alpha 合成到纯黑，再缩放到 132×176。
- 生成的是 `const uint16_t[]`，`lv_img_dsc_t.data` **直接指向它**：
  不解码、不拷贝、不占 PSRAM，代价只是 flash 多占 46KB（app 分区还有 1.1MB 余量）。
- 改锁图 = 换 `assets/lock_src.png` 再重跑脚本，别手改 `src/lock_img.c`。

## 看门狗：已整体拆除

**固件现在不会自己重启。** 以前有两套机制会把芯片复位掉，两套都拆了：

| 原来有什么 | 触发条件 | 为什么拆 |
|---|---|---|
| 任务看门狗（10 秒、panic） | `loop()` 连续 10 秒没喂狗 | 一触发就是整机复位，重启原因只留下"任务看门狗"四个字，说不出卡在哪 |
| 6 秒卡死监测（`crash_trace.h`） | `ct_heartbeat` 连续 3 次（6 秒）没推进就 `esp_restart()` | 一次"只是慢"的操作就被当成死循环复位掉 |

第二套杀伤力更大：NVS 分区越碎写越慢（几秒很正常），一次"保存配置"就可能
顶满 6 秒被判死。现场表现是**"连蓝牙就重启、一存配置就重启"**，而固件日志里
什么异常都没有 —— 更糟的是重启一次现场也就没了，越重启越没法查。

**板子已经把复位线引出来了**（见上面「引脚表」），真出问题时可以自己按复位
重来；那次重启是**有意为之**的，原因也就说得清。反过来，固件自己重启会把
问题彻底掩盖成"用着用着突然重启"。

### 拆的时候别漏这几处

- `setup()` 里三步：退订 loopTask → 把 TWDT 改成"1 小时超时 + 不 panic" →
  整个 TWDT 关掉。三步互相独立，任何一步失败都不影响"不再重启"这个结论。
  ⚠ Arduino 2.0.17（IDF 4.4）**没有** `esp_task_wdt_reconfigure()`；
  `esp_task_wdt_init()` 在已初始化时本身就是"改配置"，所以 2.x 分支直接调它。
- `esp_task_wdt_reset()` 全清了。但**不是删掉就完事**：这些调用点原本也在
  报心跳，所以换成了 `ct_alive()` —— 心跳现在是纯诊断量，开机那张"上次现场"
  的卡片靠它区分"跑了很久才崩"和"刚起来就崩"。
- `crash_trace.h` 里的监测任务删了，但**崩溃现场记录整套留下**（`ct_rec`、
  `ct_mark()`、栈溢出钩子）—— panic 之后 USB 会重新枚举、PC 上抓不到回溯，
  现场只能留在芯片里（RTC 慢存）。

### 唯一剩下的重启入口

**长按静音键（MUTE）** —— 固件里现在只剩这一处 `esp_restart()`。
重启前先闪一张大提示「系统重启 / 请稍候」并停 1.2 秒（大提示只亮 2.4 秒，
停 600ms 根本来不及看清那四个字）。

### 崩溃现场多了"跑了多久"

`ct_rec.uptimeMs` 以前只有卡死监测任务在判死的那一刻才写，现在由 `loop()`
的 1Hz 节拍自己维护。开机第三张诊断卡（"上次死在"）会带上它：

```
上次死在  按键分发 12分    ← 跑了 12 分钟才崩 → 多半是某个具体功能触发
上次死在  启动未完成 0秒    ← 刚起来就崩 → 多半是启动期就坏了
```

## HUD 提示（分大小两档）

提示是"刚才那下按没按上"的唯一反馈，所以它既要**看得见**，又不能**吵**。

| | 尺寸 | 样式 | 停留 | 用在哪 |
|---|---|---|---|---|
| **大提示** `triggerHudBig()` | 232×112 | 抬升面底 + 4px 语义色描边 + 白字标题 + **数值压在实心色块上（黑字）** | 2.4 秒 | 出错、警告、键盘被锁 / 要重启这类**必须看见**的 |
| **小提示** `triggerHud()` | 216×58 | 抬升面底 + 1px 中性描边 + 次级色标题 + **语义色数值** | 1.1 秒 | 例行确认："已保存""已开启""静音切换" |

- **为什么大提示是实心色块**：这块屏是纯黑底的，黑底卡片配 2px 细描边在
  240×240 上只是"那儿有东西"，余光一扫就滑过去了；反过来，一块实心色 +
  黑字是这块屏上对比最强的组合，隔半米也能读出来。
- ⚠ **字号动不了**：中文只有 16px 一种字号（`lv_conf.h` 里只开了
  `lv_font_simsun_16_cjk`），再大就得重生成一份子集字库。所以"醒目"靠的是
  **色块、对比和尺寸**，不是字号。
- **两行文字的行距按 19px 算，不是 16**。`lv_font_simsun_16_cjk` 的
  `line_height` 是 **19**（= `HINT_LINE_H`）。小提示原来卡高 52，标题在
  y=6、数值在 y=-5 —— 按 19 算的话两行**正好重叠 1px**，看着就是"两行字
  粘在一起"。现在卡高 58，两行顶边定死 9 / 32。
- **强调色只在一处**。小提示原来一个语义色用了三次（2px 描边 + 左侧竖条 +
  标题文字），又花又看不出重点；现在语义色只在**数值**上（数值才是要读的
  那半句），标题退成次级色 `CLR_TEXT_DIM`，描边保持中性 `CLR_STROKE`，
  左侧竖条整个去掉。大提示同理：去掉顶部实心横条、标题改白字，
  语义色只留描边和数值块两处。
- **同一条提示只改文字、不重建卡片**。重建的话卡片在旋钮连拧的时候会一闪
  一闪地抖（每转一格就 `lv_obj_del` + 建一遍）；"在原地刷新"看起来就是一条
  稳定的提示。实现是 `hudRefreshText()`，顺带把语义色也一起换（绿色的
  "已保存"被红色的"保存失败"顶掉时，颜色得跟着变）。
  ⚠ 两档的"颜色放在哪"不一样，**不能共用一套刷新逻辑**：大提示刷描边和
  色块，小提示刷数值文字的颜色。
- **通知面板在场时 HUD 让路**：通知是 228×196 的大卡片，HUD 压在它下面两边
  都看不清，两张卡叠着比只有一张更糟。
- **改排版先改 mock**：`python mock_hud.py` 出 `assets/mock_hud_big.png` /
  `mock_hud_small.png` / `mock_hud_big_compare.png` / `mock_hud_small_compare.png`
  （改前/改后对照）。里面的坐标和
  固件一一对应，改了固件那边也要改它 —— 免得烧进去才发现字挤到边上。
- **屏上本来就有反馈的，根本不弹提示**：改了主屏风格、换了屏保风格、拧了
  灯效 / 背光 / 亮度、存了设置、刷新了温湿度、清了计数、媒体播放/暂停/切歌、
  滚动字幕、确认通知 —— 这些屏幕上当场就变了，再压一条提示纯属多一次打扰。
  现在只剩 ~50 个触发点，其中 15 个是大提示。

### 加新提示的规矩

1. **先问"屏上是不是已经变了"**。变了就别弹。
2. **出错和警告用大提示**（红 / 琥珀），例行确认用小提示。
3. `hudUrgent()` 按**语义色**自动分档（红=出错、琥珀=警告）——
   ⚠ 它比的是 **RGB565 里的原始值**（`.full`），不是 RGB888。`LV_COLOR_DEPTH=16`，
   `0xF87171` 存进 RGB565 再取出来已经不是原来那个数了（会差 1~2），直接比
   RGB888 会永远不相等 —— 那样所有错误提示都会被当成例行消息降级成小提示，
   正好把最该看见的那类藏起来。
4. `mkLabel()` 收的是 `0xRRGGBB` 的 `uint32_t`，而 `lv_obj_set_style_*_color()`
   收的是 `lv_color_t`，中间用 `hudRgb()` 转。**别把 `lv_color_to32()` 的
   结果直接拿去用**：它返回 `0xFFRRGGBB`（带 alpha），高 8 位的 `0xFF` 会串到
   红通道上，青色会变成玫红。

## 显示模式

主屏有 **8 种**风格，LOGO 键短按 / 菜单「切换显示风格」循环切换，
当前风格记在 NVS 的 `disp_mode`（0~7）。

| # | 名称 | 内容 |
| --- | --- | --- |
| 0 | 极客仪表盘 | 时间 / 日期 / 温湿度卡 / 击键数 / 中间按键反馈 |
| 1 | 大字时钟 | 简约大号时间 |
| 2 | 信息面板 | 时钟卡 + 三颗锁状态胶囊 + 最近按键 + 击键数 |
| 3 | 击键监控 | 最近按键特大号 + 累计击键 |
| 4 | 律动 | 24 根柱子随击键起伏（独立 16ms 快节拍） |
| 5 | 壁纸 | 壁纸铺满 + 底部通栏信息条（时间/日期） |
| 6 | 高对比度 | 纯黑 + 横向驾驶舱：LED 顶栏 / 时-日卡 / 键名卡 / 状态行 |
| 7 | **方案按键** | 左列**当前方案那一个**图标 + 右侧大字按键 + 右下今日次数 + 底部温湿度两条窄条 |

### 「方案+按键」（模式 7）

整页就三块：**顶栏一行字 + 左列一个方案图标 + 右侧按键**，极简。

```
┌────────────────────────────────┐  y=0
│ YYQ键盘          [NUM][CAPS][SCR] │  标题靠左，三颗**长方形**锁灯靠右
├────────────────────────────────┤  y=28
│  ╭─────╮   ┌────────────────┐  │
│  │  🍎  │   │                │  │
│  │      │   │      Space     │  │  按键名（字号按实测字宽动态选）
│  ╰─────╯   │                │  │
│            │          1284  │  │  右下：今日按键数
│            └────────────────┘  │
├────────────────────────────────┤  y=204
│ 温度 ▓▓▓▓▓░░░░░░  23.5°C        │  两条窄条
│ 湿度 ▓▓▓▓▓▓▓░░░░   48%         │
└────────────────────────────────┘  y=240
```

几个实现要点：

- **这一页不建 `dashTopBar()`**，顶栏是它自己的：左上角「YYQ键盘」+
  右上角三颗长方形锁灯（亮 = 整颗填语义色，灭 = 暗底灰字）。
- **左列只画当前方案那一个图标**（白苹果 = macOS，蓝 Windows = Windows），
  下面是块 61px 的圆角底卡，**不再挂「方案」两个字**。原来试过把两个方案
  上下排、当前点亮另一个压灰，实测在 240px 屏上**压灰那版只剩一团灰影、
  分不出哪个是当前**，所以砍成只留一个。
  图标底卡的顶边（82）就是按键名 label 的顶边，图标和那行大字共用一条上边线。
- **图标底卡和按键卡是同一种材质**（同底色 `CLR_SURFACE` + 同 1px 描边 +
  同圆角）。原来图标底卡用抬升面 `CLR_SURFACE_2`、按键卡用 `CLR_SURFACE`，
  一深一浅，一眼就分成了两个互不相干的块（用户原话："块不要区分的这么明显"）。
  现在只靠**大小和位置**分主次 —— 小方块是图标、大长方是按键，主次本来就
  看得出来，不需要额外的亮度差来强调。
- **按键名的字号是量出来的，不是按字符个数定的**。montserrat 48px 下
  `Space`=148.1px、`RIGHT`=154.0px 放得下（卡片内宽 152px），但
  `NumLk`=180.3px、`DOWN`=173.0px、`NumEnt`=207.0px 会撑爆卡片 ——
  同样 4~6 个字符宽度能差 50px，一刀切按字符数必然歪一半。
  运行时用 `lv_font_get_glyph_width()` 量（带 kerning），
  在 48 / 28 / 24 里挑放得下的最大档。
  离线量字宽的工具是 `lvgl_font_width.py`（直读字体 `.c` 的 `adv_w`）。
- **按键名是主强调青 `CLR_ACCENT`，不是白**。原来白字在这一页出现**四处**
  （标题「YYQ键盘」/ 按键名 / 温度数值 / 湿度数值），48px 的主角跟 14px 的小字
  在颜色上完全没分开 —— 反而是右下角那个紫色的「1284」因为有颜色、更抢眼，
  主角被配角压住了。字号已经顶到 48px（能开的最大档）没法再加，
  **加色相**是唯一还能提层次的手段：OLED 上高色度的颜色比纯白更"跳"。
  选青不选别的：青是这套配色的主强调色（语义上就是"最重要的那个"），
  和左边的 Windows 蓝旗是同类冷色、和谐不打架；琥珀会和温度条同色、

### 引脚表

固件里的定义全在 `src/lvgl_s3.ino:386-428`，改接线先改那里。

| 功能 | 引脚 | 备注 |
| --- | --- | --- |
| LCD SPI SCK / MOSI / DC / CS / RST | 4 / 16 / 15 / 5 / -1 | `tftSPI.begin(4,-1,16,5)` 显式指定 |
| I2C（MCP23017）SDA / SCL | 14 / 13 | 400kHz |
| SHT31 SDA / SCL | 17 / 7 | 独立第二条 I2C 总线 |
| 矩阵行脚（S3 直连 10 根） | 1,2,42,41,40,39,38,47,21,12 | `rowPins[]`，列脚全在 MCP23017 |
| C3 串口 RX / TX | 10 / 9 | 接小 MCU |
| **MCP23017 RESET** | **11** | 低有效，10kΩ 上拉（见下方实测电压说明） |

⚠ `MCP_RESET_PIN` 只能是 11 这个空闲脚 —— 11 不在 `rowPins[]` 里，
SPI 也是显式指定引脚（不占 11）。GPIO11 在 ESP32-S3 上是 FSPI 的默认
数据脚，但这块板走 `tftSPI.begin(4,-1,16,5)` 显式重映射，所以安全。

**RESET 上拉实测电压（2026-10-18 万用表实测）**：MCP23017 模块的 VCC 是
**3.7V**，所以 RESET 的上拉接到它自己的 VCC 在这块板上是可行的 ——
芯片的输入高阈值 VIH = 0.8 × 3.7 = 2.96V，而 GPIO11 写高是 3.3V，稳过。
本板实测用 4.7kΩ 接到 VCC，键盘正常工作。

⚠ 但**换板子时不要照抄**：3.7V 已经是 ESP32-S3 绝对上限（3.3V+0.3V = 3.6V）
的边缘了，只是 MCP23017 引脚容差宽才没出事。上拉接到 3.3V 永远安全，
接模块 VCC 只在实测确认 VCC ≤ 3.6V 时才可用。

### ⚠ 不要再给 SDA / SCL 外加上拉

这条是踩过的坑，排查时极具误导性：**给 SDA、SCL 各加一个 4.7kΩ 到 MCP23017
模块自己的 VCC，键盘会直接全哑**，而且症状和"芯片被复位"一模一样
（I2C 侧仍能探到芯片、列脚驱动不了、恢复阶梯反复重试都救不回来）。

根因是**电平**不是电阻大小：

- **ESP32-S3 的 GPIO 不耐 5V，上限只有 3.6V**。模块标注的 VCC 未必是 3.3V，
  把它当上拉电源就是在往主控引脚上灌超压电流，内部 ESD 钳位二极管会导通。
- 就算 VCC 确实是 3.3V，**这个上拉也是多余的** —— 模块板上本来就自带
  （绝大多数 MCP23017 breakout 都有 4.7k/10k）。I2C 能正常工作本身就是证据：
  没有上拉的话 SCL/SDA 会一直贴着地，根本通不了。

同理，RESET 的 10k 上拉也**只能接 3.3V**，不要接模块 VCC。

判断该接哪条轨的正确做法是**先量电压**，不是看丝印猜：

```bash
# 万用表黑表笔接模块 GND，红笔笔尖依次碰 VCC / SCL / SDA
# 读数是 3.3V 上下才算可以拿来做上拉；出现 5V 就一律不许接主控
```

顺带一提：SDA 脚被 5V 灌过之后要留意后续是否有 I2C 偶发失败，
那种"时好时坏"的故障要第一个怀疑这颗脚。

### MCP23017 卡死：自动检测 + 自动硬复位

**现象**：偶发。按住空格（或者 A、I 之类的常用键）不放，主机那边会**连续收到
6~7 次**这个键，然后整个键盘失灵，必须断电。

**根因**：某一根列脚被芯片死死按在低电平不放。一轮扫描结束时所有列脚本来都该
回到高电位，此刻无论用户按着几颗键，行脚都必须读回高 ——「按下」在电气上只是
把行脚接到列脚上，而列脚是高电位，中间没有低电位源。所以「所有列都放开时行脚
读到低」只有一个解释：**芯片正在驱动一根本该放开的列**。那一列被按死，行脚就一直
读到「按下」，而总线又时通时不通让这个读数反复翻转；每次翻转只要稳定满 20ms，
三态消抖就认一次账 —— 物理上按了一次，主机收到 6~7 次。之后总线彻底废掉，
全哑。

固件现在有三路探测，任何一路判死都会走 GPIO11 自动硬复位自救：

| 探测 | 周期 | 抓什么 |
| --- | --- | --- |
| 空闲态行脚检查 `mcpIdleRowsClean()` | 每拍 8ms，连续 2 拍判死 | 某列被按死 —— 连发的直接根源 |
| 同键连发计数 `mcpGhostBurstAt()` | 每拍 8ms，认账时计数 | 故障时好时坏、撑不满一整轮的短命故障 |
| 列选全量自检 `mcpColumnStrobeOk()` | 每 500ms | 寄存器配置丢失（芯片活着但全是输入态） |

**为什么前两路必须存在**：6~7 次连发本身需要 12~14 次翻转 × 20ms 消抖 =
**240~280ms**，而原来只有 500ms 的自检，且它跟故障起点毫无关联。能不能赶在
连发发出去之前检测到**全看 tick 落在哪里** —— 这正是它偶发的原因（运气好 0 次，
运气差 6~7 次全打进正在编辑的文档）。换成每拍都跑之后，最坏 16ms 判死。

同键连发判据是「同一颗键 400ms 内被认下 4 次按下」。人手做不到（世界纪录手速
也得 ~100ms 一次），而半死的总线正好批量生产这个形状。它卡在**任何分发之前**，
所以幽灵按键不会走到主机。

判死之后：不再盲扫（盲扫只会产生更多幽灵键）→ 走四级恢复阶梯，第 1 级就是
`mcpHardwareReset()` 拉 GPIO11，不经过 I2C，总线已经废了照样生效 → 成功后清空
消抖和按住状态。连续「刚恢复就又坏」3 次会把重试间隔从 300ms 退到 2s，并在日志里
明确提示去查 RESET 焊点和芯片 —— 那种情况软件救不了，该动烙铁。

**开机诊断屏**的「键盘扩展」那一张会显示累计自动复位次数（`复位N`，NVS 键
`mcp_recover_n`，**跨重启保留**）。必须落盘是因为遇到失灵的用户十有八九已经重启过
一次，只放内存里的话开机看到永远是 0。颜色含义：绿=线通且没发生过复位，
橙=线通但发生过复位（这机器有过 I2C 干扰，值得留意），红=复位线不合格。

#### 双击 CPG 键 = 手动重启 MCP23017（不重启整机）

**连按两下灯效键（CPG，间隔 ≤350ms）会重启键盘扩展芯片 MCP23017，而不是重启
整个 S3。** 屏幕上弹一行「键盘扩展已重启 / MCP23017 复位完成」；失败则弹红色
「正在自动恢复」。

之前这个键的长按是 `esp_restart()`（整机重启），代价太大 —— SPIFFS / BLE / USB
协议栈全套重来，几十秒黑屏。用户想解决的往往只是「键盘不灵了」，把扩展芯片
复位一下就够了，不该连累整机。

走的是 `mcpRestartChip()`，五步顺序不能换：拉 GPIO11 复位脚 → 重建 I2C 外设 →
重新初始化 + 重刷列配置（复位后寄存器回到 `0xFF` 全输入，不重刷 16 个列脚一个
都不驱动）→ 列选自检 → 清消抖和按住状态（否则会冒幽灵键，主机那边还会永远按着
一个组合键）。

**长按 CPG（3 秒）仍然重启 MCP23017** —— 它是双击之外的兜底。两者互不干扰：
C3 那边按住满 3 秒只发 `BTN:CPG_HOLD`、不会再补发 `BTN:CPG`，所以长按永远
凑不成双击。

**长按静音键（MUTE）是整机重启** —— 看门狗拆掉之后，它是固件里**唯一**一处
`esp_restart()`（详见下面「看门狗：已整体拆除」）。
**唯一例外是响铃期间**：那时长按静音会被降级成短按静音（停铃），不重启。理由见
下面「响铃时长按静音不重启」。

##### 为什么双击判定只能放在 S3 侧

**C3 小 MCU 不能刷固件**（跑的是出厂那版）。C3 只认得两种按键事件：`BTN:CPG`
（每次松开都发一次）和 `BTN:CPG_HOLD`（按住满 3 秒才发），**按下的瞬间不发
任何东西**。所以 S3 能拿到的原始信息只有「什么时候收到一条 `BTN:CPG`」，
双击只能在这儿判。

⚠ **长按阈值没法从 3 秒改成 2 秒** —— `holdDuration` 写死在 C3 固件的按钮表里，
S3 在 3 秒那一刻才收到 `BTN:CPG_HOLD`，3 秒之前它对「键还按着」完全无知。
想缩短只能刷 C3。

##### 双击窗口 350ms 是怎么定的

切换灯效是「**看着结果**再按下一次」的反馈型操作，两次按键天然被人的视觉反应
时间（250~400ms）隔开；而故意双击的人也是这个量级。窗口太紧 → 双击打不中，
用户以为功能坏了；太松 → 连着快速切灯效时误触发重启（这个代价小：重启只花
30ms，键盘照常用，屏幕上还有 HUD 明说发生了什么）。

**单击切灯效保持零延迟**：第一次点击照常立刻切灯效，不为了双击把它延后 350ms
—— 那个功能的使用频率比双击高得多，延迟会明显变钝。代价是**双击之后灯效会前进
一档**（第一次点击已经切过了），这是「单按=切灯效 / 双击=重启芯片」两个语义
共用一个键的必然结果。第二次点击则**不再切灯效**，否则双击会连切两档。

⚠ 手动重启这条只做了「复位 + 重建」，失败时会把 `mcpHealthy` 打成 false，让扫描
主循环里的完整四级阶梯接手（那边还有 12/40 拍时钟救援）。不这么做的话，手动重启
失败之后键盘会一直保持半死状态 —— 自愈阶梯只对「已被判定为死」的芯片动手。

## 改完界面文案后必须重生成字体

界面里的中文是靠 `src/lv_font_simsun_16_cjk.c` 这个子集字库渲染的。
**在 .ino 里新增/修改任何中文后，要重跑一次字体生成**，否则新字会是空白：

```bash
python gen_font.py    # 重新生成 lv_font_simsun_16_cjk.c + charset.txt
python check_font.py  # 确认 MISSING 为 0
```

`gen_font.py` 会扫 .ino 里的字符串字面量 + 一份兜底词表，用 `C:\Windows\Fonts\simhei.ttf`
生成 16px / bpp=4 的子集，并挂上 `fallback = &lv_font_montserrat_14`。

> ⚠️ 别把参数改回 `--symbol charset.txt`。这版 lv_font_conv 的 `--symbols`
> **不读文件**，参数值会被当成字面字符（见 `node_modules/lv_font_conv/lib/collect_font_data.js`），
> 结果就是字库里一个汉字都没有、界面全是豆腐块。脚本改成传 `-r` 码点区间（纯 ASCII，
> 不会被 Windows 的 cmd + GBK 代码页改写）。

字体相关约定：

- `LV_FONT_DEFAULT` 指向中文字体 → 凡是没显式指定字体的控件都能出中文
- 需要显示中文的 label 显式用 `&lv_font_simsun_16_cjk`（方案名 / HUD / 通知条）
- 纯英文数字的控件继续用 `lv_font_montserrat_*`，观感更好

## 屏幕与按键的约定

- 主屏是真正的 `lv_obj_t` 屏幕对象，由 `ensureMainScreen()` 建/取，
  6 种主屏风格都建在它上面。**不要**改回 `lv_obj_create(lv_scr_act())`。
- 6 种风格的根容器统一用 `makeRootPanel()` 建，**不要**再手写 `lv_obj_create` +
  `set_size/pos`。原因：LVGL 默认主题给普通 `lv_obj` 套了 `card` 样式（`pad_all = 13px`
  @DPI130），而 `lv_obj_set_pos()` 会走 `lv_obj_move_to()`，**把父对象的 pad+border
  叠进子对象坐标**。于是任何"贴在 (0,0)"的子对象都会右下偏 13px，右边和下边被裁掉
  —— 表现就是"整个界面往右移了一点"、壁纸模式下尤其明显。用 `lv_obj_align()` 的
  子对象不受影响（对齐算 content 区中心，pad 对称时中心不变），所以很容易漏。
- 顶部条（`dashTopBar()`）左三是三颗锁状态灯（NUM/CAP/SCR，只画圆点不写文字，
  外面套一圈同色细环，亮起时才显形），右边是方案指示：序号常显，1/2 号方案另配
  系统图标（Windows 四格窗 / 苹果），图标全部用 `lv_obj` 基本图形拼，改样式时
  别去动 `topIconWin[] / topIconMac[]` 的创建顺序（= 绘制顺序：果体 → 缺口 → 果柄 → 叶）。
- 三颗锁状态**翻转的那一刻**会弹一条 HUD（`updateDynamicElements` 里用
  `lockPrev[]` 比对上一帧）。顶栏那三颗灯太靠边，离远了看不出大写开没开，
  光靠变色不够。`lockPrevValid` 是"界面刚重建"的标志：重建后第一帧只记录不弹窗，
  否则每次回主屏都会一口气弹三条。
- **Montserrat 里没有汉字，也没有到中文字库的回退**（回退是单向的：
  `lv_font_simsun_16_cjk.fallback = &lv_font_montserrat_14`，反过来没有）。
  挂 `lv_font_montserrat_*` 的 label 写中文 = 一片空白。要显示中文就显式换
  `&lv_font_simsun_16_cjk`；纯 ASCII 的占位符（`--`）才可以用 Montserrat。
- 日期统一走 `formatDateCN()`（"9月27日 星期六"）。用了它的 label 必须是中文字库。
- **别用 `transform_zoom` / `transform_angle` 放大字号或做视觉效果**：
  LVGL 8.4 的软件渲染器对需要 alpha 的中间图层有一道闸门
  （`lv_draw_sw_layer.c`: `LV_COLOR_SCREEN_TRANSP == 0 && HAS_ALPHA → return NULL`），
  本项目没开 `LV_COLOR_SCREEN_TRANSP`，走这条路的控件会被**静默地整个不画**。
  要大字就上大字号的字库。
- 回主屏统一走 `gotoMainScreen()`，它负责模式复位 + 内容重建 + 切屏。
- 按键分发顺序必须和 `s3/s3.ino` 原版一致：界面态（菜单 → 设置 → 录制）先接管，
  `K_MC` 放最后。在界面态里 `K_MC` 和 `ESC` 都是"退出"。
- 宏/序列/组合键的执行链和原版 `s3/s3.ino` 一致：`executeGlobalKey()` 吃
  `GSET` 的 `SW:x+SEQ:…` / `SW:x+CMB:…`，`executeMacro()` 吃按方案的
  `p<n>_<键名>`（`SEQ:` / `CMB:` 两种）。网页端 `s3-setting.html` 发的
  `SET:p0_M1:…` 名字里已经带方案号，固件端**不要再拼一层** `p<currentProfile>_`。
- 按键编码只有**一套**在矩阵里用：Arduino 的 "0x88 + HID usage"。
  0xE0~0xE7 在这里是**小键盘回车 / 小键盘 1~7**（0x88+0x58=0xE0=NumEnt，
  0x88+0x5F=0xE7=Num 7），**不是**修饰键 —— 别在 kbPress 里把它们当 0xE0~0xE7
  的 HID 修饰键处理，一处理整片小键盘就全错（7 会变成 Win 键）。
  网页"按键映射"下拉里那几个 "🔹 Left Ctrl"=224 才是 HID 风格，它们的换算
  统一在 `normalizeRemapKey()` 里做，只作用于 remap 表的读入/读出。
- **小键盘符号键（`/ * - +`）必须用 `0xDC~0xDF`，不能退回 ASCII**。
  这里踩过两次，两个方向的错都犯过：
  · 用 HID usage `0x53~0x63` → 和 ASCII `'a'/'b'/'c'`(0x61~0x63) 数值撞车，
    基础键盘按 A/B/C 会发成 Num 9 / Num 0 / Num .（见提交 `9973f87` 的 A→9 修复）。
  · 改用 ASCII 规避撞车 → `*`=42 走 `_asciimap` 变成**主键盘 Shift+8**、
    `+`=43 变成 Shift+=，发出来的压根不是小键盘那颗键（Mac 上数字小键盘就是废的）。
  正解是 `0x88 + HID usage`：`Num /`=0xDC `Num *`=0xDD `Num -`=0xDE `Num +`=0xDF。
  这一串既和 a/b/c 不撞车，又和网页"🔹 修饰键"224~231 不撞车，走 `kbPress` 的
  `>=0x88` 分支被减回 `0x54~0x57` 交给 `pressRaw`，发出的是**真正的小键盘键**。
  效果上等于"宏里选 Num \*"和"手按物理小键盘的 \*"发同一个码点。
  小键盘数字（1-9/0/`.`）仍用 ASCII —— `_asciimap` 翻成主键盘数字，字符是对的；
  换成 `0xE0~0xE7` 反而会被 `normalizeRemapKey()` 当修饰键折算掉。
  ⚠ 网页 `s3-setting.html` 的 `KEY_OPTIONS` 是同一套值的另一个副本，**改一处要改两处**。
- 同一个坑的第二个面：**别拿 Consumer 页的 usage 去比 `baseKey`**。
  0xE2 = 0x88+0x5A = **小键盘 2**，不是静音 —— 谁在按键分发里写
  `else if (baseKey == 0xE2)` 做 Mute，小键盘 2 就会静音且不再当数字键用。
  静音键物理上挂在小 MCU **C3** 上，走 Serial1 的 `BTN:MUTE`
  （`handleC3Command`），**矩阵里没有这一格**，不要试图在矩阵里加。

## 闹钟 / 倒计时

两个功能共用一套**响铃引擎**（`ringingKind` / `startRinging()` / `stopRinging()` /
`drawRingOverlay()`）：到点了就是"响铃"这个状态，主背光整排黄灯快闪 + 屏幕上
一张常驻卡片，只有文案和中间那个大数字不同。

### 响铃时长 / 怎么停

- 停铃键**只有两个**：灯光键、静音键（用户定的）。其它键照常发给主机，
  响铃期间打字不受影响。
- **响铃时长按静音 = 停铃，不重启**。`handleC3Command` 开头就把响铃期间的
  `BTN:MUTE_HOLD` 改写成 `BTN:MUTE`，所以走的是短按那条路（静音发给主机 +
  停铃 + 确认通知）。
  - 为什么：用户长按静音八成是想让铃停下来，而不是想重启键盘。而重启的副作用
    不小 —— `alarmLastFiredYday` 是**纯 RAM** 变量，重启归零；墙钟又从 NVS 的
    `set_epoch` 恢复。只要恢复出来的时间正好落在闹钟那一分钟，开机就再响一次，
    长按几下就成死循环了。
  - 老固件 `s3/s3.ino:3948` 就是这么处理的（"响铃期间长按不当重启用"），
    lvgl_s3 搬过来时把这段丢了，这次补回来。
  - ⚠ 降级时必须清掉静音键自己的**双击配对标志**（`g_muteTapArmed`）：静音键
    还有一套"双击 = 锁定/解锁"，不清的话这次降级会被当成双击的第二击 —— 结果
    不是停铃，而是把键盘锁了，闹钟还响着键盘却按不动。
- 响铃期间**不能息屏**：`loop()` 的息屏判断会放过 `ringingKind != RING_NONE`，
  屏幕一黑就等于没提醒。起铃时 `startRinging()` 还会把 `lastActivityTime`
  拨到当下、把屏叫醒。
- 60 秒没人理会自动停铃，但会往通知队列塞一条"闹钟未确认"/"倒计时未确认"，
  不静默丢失（`RING_SAFETY_MS`）。没有这道兜底，一排黄灯能闪一整晚。
- 响铃的优先级**高于通知告警**（`renderLightingEngine()` 里响铃分支排在
  `currentAlertType()` 之前）：通知是主机推的消息，响铃是"现在不动手就来不及"。
  反过来的话会出现屏上写着"闹钟响了"、灯却在闪红的各说各话。
- 响铃期间 `sendLedFrameToC3()` 强制 `ledScale = 255`：用户可能平时把亮度调到
  很低（夜里用），按那个比例缩下去闪灯就几乎看不见了。

### 倒计时全屏

用户要求：「全屏幕就是展示这一个倒计时，文字很大」。所以倒计时跑起来时是一块
**独立屏幕**（`scr_countdown`），240x240 全部让给那一个 48 号数字，连进度条和
"按灯光键退出"都不加 —— 加了它就变成另一块主屏，那就不是用户要的东西。

- 字号：48 号 Montserrat 里数字 28~32px、冒号约 11px，最坏情况 `88:88:88`
  ≈ 203px，240px 的屏放得下。不满 1 小时只排 `MM:SS`（约 142px）。
- **按住灯光键退出全屏，倒计时继续在后台跑**（`BTN:LIGHT_HOLD`）。收走屏
  不等于取消计时；跑完照样响铃。这一路长按不会再顺手切背光总开关，
  否则"退出全屏"会把用户的灯关掉、还得再按一次才开得回来。
- 让位规则集中在 `updateCountdownVisibility()`，不要在各个调用点自己
  `showScreen()`：进菜单/设置页/录制/日志要让位，响铃中要让位，息屏要让位。
  分散判断迟早漏一处，表现就是"进了菜单底下还是倒计时"。
- 设置页那颗**开始/停止按钮原来是个摆设**：画出来了、文案会跟着
  `timerRunning` 变，但全工程没有任何一行代码处理它，回车键走的是通用保存
  分支，只把时长记进 `timerTotalSec` 就退出，一次都没起过表。现在回车键走
  `toggleCountdownFromKeyboard()`，让按钮说的话成真。

### `TIMERSET:` / `ALARMSET:` 的写法

`TIMERSET:` **三种写法都收**：

| 写法 | 例子 | 谁在发 |
| --- | --- | --- |
| 纯秒数 | `TIMERSET:300` | `s3-setting.html` / `kbctl.py` / `kbctl_hid.py` |
| `MM:SS` | `TIMERSET:05:00` | 手写脚本 |
| `HH:MM:SS` | `TIMERSET:01:05:00` | 手写脚本 |
| 停止 | `TIMERSET:STOP` / `OFF` / `CANCEL` | 网页停止按钮 |

⚠ 以前这里**只认 `HH:MM:SS`**（要求两个冒号），而**所有**远端客户端发的
都是纯秒数 `"TIMERSET:300"`，走不进分支被静默跳过 —— 网页点"启动"只弹了个
`alert`，键盘上什么也没发生。老版 `s3/s3.ino` 三种都收，移植到 LVGL 时这段
容错被漏掉了。

`ALARMSET:` 收 `HH:MM` 和 `OFF`/`0`/`DISABLE`/`CANCEL`。`kbctl.py` 关闹钟发的
是 `ALARMSET:OFF`，以前"OFF"里没有 `:` 走不进分支，**关不掉闹钟而且不报错**。
越界的时/分（`99:99`）现在会被拒掉并提示，不再截断存进 `uint8_t` 等第二天。

### 判定在哪跑

`updateTimers()`，在 `loop()` 里按整秒节流（不占任何中断）：

- **闹钟**：只在"当前这一分钟"命中，再用 `tm_yday` 去重保证一天只响一次
  （不加 yday 会连着响一整分钟）。`tm_year <= 124`（时间没校准）时不判定，
  否则开机瞬间正好撞上 `00:00` 的闹钟会莫名其妙响一次。
  这正是以前"设了闹钟不响"的根因：`alarmLastFiredYday` 声明了却一次都没被读过。
- **倒计时**：剩余量从 `millis() - timerStartMs` **反算**，不是每秒自减 ——
  中间被宏的 `delay()` 或壁纸解码阻塞几百毫秒也不会越欠越多。
  同样是以前只赋值、从没被减过。

## 灯效

- 灯光设置页五个字段：背光开关 / 背光亮度 / 灯效 / 状态灯亮度 / **按键灯效**。
- 按键灯效（`keyFxStyle`，存 NVS `key_fx`）是**叠加层**：按下任意键时
  `triggerKeyReaction()` 置状态，`renderLightingEngine()` 每帧把 0~15 主背光
  先压暗到 ~40%（原版 `updateKeyReaction()` 的 `*102>>8`），再把特效那几颗点亮。
  涟漪=从正中向两侧扩散 / 发射=从末位往回扫子弹 / 堆叠=从末位往回填。
  颜色每按一次自动换一种（原版"自动"档的配色）。
- 叠加层必须写在基础灯效**之后**，顺序反了会被灯效盖掉；告警期间整段不走
  （`renderLightingEngine()` 在告警分支就 return 了），16~18 锁状态灯也不受影响。
- 主背光一共 **16 颗（0~15）**，16/17/18 是三颗锁状态灯。别再把 `0~15` 写成
  写死的 `15`（`i < 15`）—— 那样第 16 颗主灯在常亮灯效下永远是黑的。

## 系统菜单（两级）

一级只列 8 个大类，回车进去才看到该组的具体项：

| 一级 | 二级 |
| --- | --- |
| 显示 | 切换主屏风格 / 切换屏保风格 |
| 灯光 | 灯光设置 |
| 时间 | 设置时间 / 闹钟设置 / 倒计时 |
| 键盘 | 切换配置方案 |
| 温湿度 | 刷新温湿度 / 温度校准 |
| 系统 | 计数清零 / 错误日志 |
| 帮助 | 按键速查 |

- 菜单项要执行什么走 `MenuAction` 枚举 + `runMenuAction()`，**不要按数组下标
  switch** —— 一旦分组重排，下标就全变了。
- `menuSel` 是一级大类下标，`menuItemSel` 是组内项下标，`menuInSub` 决定当前
  在哪一级。ESC 在二级是"回一级"、在一级才是"退出菜单"。
- 列表按 `MENU_ROW_MAX` 建满行、切换层级只改可见性和文字，不整屏删建
  （LVGL 8.4 删活动屏会把 `disp->act_scr` 置 NULL）。
- ⚠ `MENU_ROW_MAX` **必须 >= `MENU_GROUP_COUNT`**。这个数组只建这么多行对象，
  超出这个数的大类**既不画出来也不报错**，表现是"菜单项能选中、能进去，
  但屏幕上就是看不见那一行"，非常像被什么盖住了。
- 已删除的"按键回显开关"：那个 `showKeystrokes` 是纯内存变量、**不落 NVS**，
  每次开机都被初始化回 true，用户关掉、插电或重启一次就自己弹回来。
  而它唯一的用途就是让主屏上那颗"最后按下的键"显示 `--`，没有实际价值。

## 按键速查（菜单 → 帮助 → 按键速查）

这块板子上的功能已经多到记不住了 —— 灯光键短按切控制目标、长按切背光、
静音键双击锁键盘、CPG 键双击重启扩展芯片……全靠记忆迟早要出事。
所以在菜单里放一张表，随时能翻。

- **形态**：独立屏幕，但画成"浮在暗底上的对话框"（深底 + 居中卡片 + 强调色描边）。
  桌面预览用 `mock_help.py` 出图（`assets/mock_help_3x.png`），改排版先改它。
- **不做成菜单屏的子对象**（那样菜单能透出来，更像真模态）：菜单屏会被
  `build_menu()` 重排、被换屏换掉，浮层挂在它身上等于把生命周期绑在别人身上；
  更要命的是从菜单退回主屏 / 进屏保之后浮层会"跟着复活"—— 表现是"关掉速查表
  之后，下次打开菜单它又自己冒出来了"。
- **内容表只有一处**：`helpItems[]`（左列"按什么"、右列"会发生什么"，
  外加 `HELP_HEAD` 分组标题）。改内容改这一张表就行，排版、滚动、位置指示
  都是自动的。
- **滚动是手动窗口**（和错误日志页同一套 `elogScroll` 写法）：LVGL 自带的滚动条
  要靠手指/滚轮驱动，这块板子上只有旋钮，拧不动它。旋钮、↑↓、PgUp/PgDn 都能翻。
- **两列宽度是量出来的**，不是估的（`text_width.py` 读真实字库的 `adv_w`）：
  左列 92px（最宽"静音键 短按"= 88px），右列 108px（最宽"锁定/解锁键盘"= 104px）。
  写长了会被省略号截断，所以改文案之后先跑一遍
  `text_width.py --margin 92 "..."` 核一下。
- `SYS_MODE_HELP` **要**进 `scanKeyboardMatrix()` 的 `inUiMode`：速查表是纯查阅
  界面，在里面打字没有意义，矩阵键照常发主机只会把主机屏幕搞得莫名其妙。

## 底部按键提示（务必先量宽度）

屏只有 240px 宽，提示行是 16px 中文字体。`adv_w` 在 LVGL 里是 **1/16 px 单位**，
实际像素 = `adv_w / 16`；汉字 16px、ASCII 8px、`·` 8px、方向箭头 **也是 16px**。

原来那些一整行的提示实际有多宽（用 `text_width.py` 量）：

| 文案 | 宽度 | 屏宽 240 |
| --- | --- | --- |
| `←→ 切换 · ↑↓ 调整 · 回车保存 · ESC 取消` | 368px | 溢出 128px |
| `←→ 切换 · ↑↓ 调整 · 回车开始/停止 · ESC 取消` | 408px | 溢出 168px |
| `↑↓ 翻看 · DEL 清空 · ESC 返回` | 264px | 溢出 24px |
| `上下选择 · 回车确认 · ESC 返回` | 256px | 溢出 16px |

居中对齐后左右各裁掉一半，用户看到的就是"底部的字跑出屏幕"。

- 字库是 Windows `simhei.ttf` 生成的 16px 固定字号，**重生成小一号中文字库需要
  Windows 字体源**，开发机上做不了。所以只能拆行 + 砍字。
- 现在统一走 `mkHintLine()` 造**两行**（`HINT_LINE1_Y` / `HINT_LINE2_Y`），
  这是唯一能一条按键说明都不丢的办法 —— ESC 是设置页唯一的"不保存退出"路径，
  压成一行就得砍掉它。
- 每个提示 label 都带 `lv_obj_set_width(HINT_W)` + `LV_LABEL_LONG_DOT`，
  这是硬兜底：以后谁加了超宽文案，超出部分只会变省略号，不会画到屏幕外。
- 加新文案前先跑 `python text_width.py "你的文案"`，超 216px 就是放不下。

## 息屏 / 屏保

- 「显示 → 切换屏保风格」在 黑屏 → 壁纸轮播 → 信息面板 → 关闭 之间循环
  （存 NVS `saver_mode`）。
- **"关闭"这一档不建屏保屏**：空闲到时什么也不做，主屏一直留着
  （`loop()` 的超时判定里 `saverMode != SAVER_OFF` 直接短路）。这也是默认值。
- 档位编号是 NVS 持久化的，**只能往后追加、不能往前插**：原来的
  `SAVER_OFF = 0` 语义是"黑屏"，那个语义现在归 `SAVER_BLACK`。
  把"关闭"插成 0 的话，老用户开机就变成屏保关着，属于静默改设置，
  所以 `SAVER_OFF = 3` 追加在末尾，0/1/2 三个旧值的含义一字不变。
- **壁纸轮播**：壁纸铺满 + 底部一条**通栏信息条**（时间/日期/温湿度）。
  信息条是 `sv_panel`，贴在屏幕底部 72px（`BAR_Y = 240 - BAR_H = 168`），
  **无描边无圆角** —— 它是"界面结构"，不是"贴上去的控件"。
- 屏保面板**不再每 5 秒闪一次**。旧版是 204x112 的不透明大卡片贴着壁纸正中，
  把"YYQ"主标和律动条整片盖住，只能靠"藏 5 秒 / 露 5 秒"来轮流，
  每次切换都是一次突兀的闪。现在卡片改成底部通栏条，只压住图片最下面一条，
  主标和表盘全都露在外面 —— 不需要让位，也就没有理由再闪。
  （`SAVER_INFO` 纯信息屏没有壁纸，居中一张卡片才是对的形态，那一档保留原样。）
- 壁纸主屏（风格 6）的时钟同样改成**底部通栏条**（`BAR_H`/`BAR_Y`，
  和屏保用的是同一套坐标）。原来那块 112x40 的小卡片带 1px 描边 + 圆角，
  浮在壁纸正中偏右，而壁纸的构图是连续的圆弧 —— 矩形正好把弧线挖断，
  一眼看过去就是"有张便利贴贴在图上"，这就是"时钟很突兀"的来源。
- **固件和壁纸图是硬约定的**：条的上边缘 `BAR_Y = 168` 必须和壁纸图里
  表盘圆弧的最低行对齐。改任何一边都要改另一边，否则条会压到弧线、
  或者下方露出没清干净的残留。
  `check_consistency.py` 会把两边的定义读出来互相校验 + 实测像素：
  ```bash
  /usr/bin/python3 check_consistency.py
  ```
- 壁纸图本体用 `wallpaper/gen_wallpaper_240_v2.py` 生成（纯黑底 + 矢量描边）。
  不用 AI 底图：1024 的图缩到 240，辉光会被 JPEG q95 + RGB565 吃掉，只剩一团脏灰。
  底部 72px 刻意留空给信息条，脚本跑完会自检那块区域一个非黑像素都没有。

### 壁纸上传：两条路（解码在电脑端 or 在板子上）

| | 网页端 `s3-setting.html` | 命令行 `tools/send_wallpaper_raw.py` |
|---|---|---|
| 线上格式 | `LOGO_JPEG_START:<n>` + JPEG 字节 | `LOGO_RAW_START:115200` + RGB565 字节 |
| 解码在哪 | **板子上**（JPEGDEC） | **电脑端**（PIL） |
| 字节数 | 约 14 KB | 115200 字节（240×240×2） |
| 板子要不要 JPEGDEC | 要 | **不要** |

**RAW 那条路是"解码在电脑端做、板子只收 + 展示"** —— 和传 M1 宏数据是同一套路：
这边发什么，那边就显示什么。板子上只搬字节，没有解码器，也就没有解码那一类崩溃面
（JPEGDEC 那个对象 12.6KB 静态占着内部 DRAM，而且解析时要在输入缓冲里大量跳转，
输入缓冲一旦在 PSRAM 上就不稳 —— 之前"上传壁纸必崩"就踩在这上面）。

RAW 的长度是**固定**的 `240*240*2 = 115200`，不是主机随口说的数，所以板子上
不存在"声明多少就收多少"的越界可能（JPEG 那条之所以需要一个 256KB 的常驻缓冲，
就是因为长度可变）。落盘格式两者完全一样：`/logo.bin` = 240×240 的 RGB565，
所以开机读回那套逻辑（`loadWallpaperFromDisk`）一行都不用改。

**字节序是硬约定**：`LV_COLOR_DEPTH=16` 且**没有**开 `LV_COLOR_16_SWAP`
⇒ RGB565 就是 ESP32 上的 native 小端。电脑端按小端打包，固件里 JPEGDEC 用的
`RGB565_LITTLE_ENDIAN` 落在内存里也是这个样子，两条路写进 `wpPixels` 的字节一致。
`check_consistency.py` 会把这条约定一起校验。

```bash
# 传新壁纸（自动完成 START → 握手 → 分片 → FLUSH → 等落盘 → 切壁纸主屏）
cd lvgl_s3 && /usr/bin/python3 tools/send_wallpaper_raw.py

# 顺便导出"解回来"的 PNG 对照，肉眼核对打包对不对
/usr/bin/python3 tools/send_wallpaper_raw.py --verify
```

⚠ **握手不能省**：`LOGO_RAW_START` 是文本命令，在 loop 任务里处理；而二进制分片
走的是蓝牙协议栈任务的 probe（判据是 `logoRxActive`）。BLE 的 ATT 写响应是
协议栈**收到包就回**的，不代表 loop 任务已经处理完 —— 第一片二进制完全可能
抢在 START 前面到，那一片会被当成文本命令吞掉。所以发第一片之前必须轮询
`LOGO_STATUS`，等固件回报 `RAW:0/115200`。

## 文件系统与分区（别踩）

- 壁纸 `/logo.bin` 和 ME 文本 `/me_hex.txt` 存在 **SPIFFS** 上，**不是 FFat**。
- 板子默认分区表（PlatformIO 的 `default_8MB.csv` / Arduino IDE 的 `default.csv`）
  里只有 `spiffs` 分区，**没有 ffat 分区**。`FFat.begin()` 找不到 subtype=fat 的分区
  会直接返回 false，之后每次 `FFat.open()` 都是一个无效 File —— 表现就是
  "ME 文本存入失败""壁纸重启就丢"。
- 所以烧录时的分区方案必须是**默认那几档**（带 spiffs 的）；选了
  "16MB Flash (3MB APP/9.9MB FATFS)" 这类 FATFS 方案，SPIFFS 反而会挂不上。
  （`lvgl_demo/` 那个 README 让人选 FATFS，是历史遗留，别照做。）
- 分区表别改：宏 / 按键重映射 / 方案 / 灯光 / 校准值都在 `nvs` 分区，
  挪动偏移等于把用户配置全抹掉。

## 蓝牙收发（`src/bt_link.h`）

**蓝牙的收和发只走 `bt_link` 一个模块。** 业务代码不碰分片、不碰终止符、
不碰心跳计数，网页那边也只面对同一套规则。改协议必须**两边同时改**
（`src/bt_link.cpp` + `../s3-setting.html` 里的 `BtLink`）。

### 线上格式

一条消息 = 若干片 + 一条收尾标记，**包终止符是 `\r`**：

```
VERB:KEY:<正文片段>\r      0~N 条
VERB:KEY:LEN:<总字节数>\r  流式回复才有，正文第一片之前
VERB:KEY:END\r            每条消息都有（正文 0 字节时也发）
```

- `VERB` / `KEY` 非空、不含 `:` `\n` `\r`
- `KEY` 优先用**请求号**（1~9999），不要拿业务字符串当 key
- 正文按 **UTF-8 字节**算，中文一个字 3 字节

### `LEN:` 那一行不是可选的

`btLinkStreamBegin(verb, key, totalLen)` 的 `totalLen` 会先发成一条
`LEN:<总字节数>`。主机收到 `END` 时拿它和**实际收到的 UTF-8 字节数**对一遍，
对不上就报"传输丢片"、**不把残缺正文交出去**。

原因：分片发送丢片是**静默的** —— 一条 ATT 通知带不下就被协议栈整条丢掉，
而收尾标记照样会到。没有总长做对照时，主机只有"看着像完整的"这一个依据：

- 运气好 → `JSON.parse` 报 `unexpected end of input`（还能看出是丢片）
- 运气不好（正好切在某个 `}` 上）→ **语法合法但缺内容**，页面照着它显示，
  甚至照着它回写，把缺掉的字段静默清零

早期 `bt_link.cpp` 里这里是 `(void)totalLen;`（注释写着"只是诊断信息"），
就是上面第二种情况的来源。改协议时**两边都要认这条行**：网页端把它单独
识别、**不拼进正文**；旧网页遇到它会把 `LEN:xxx` 当正文开头，所以改完要
连页面一起换。旧固件不发这一行，网页端会跳过核对（向后兼容）。

### 固件侧：发

```cpp
btLinkReplyC("REMAPDUMP", body);            // 处理请求的分支里回话（推荐）
btLinkReplyf("GKEYPHASE", "%u", ph);        // printf 风格
btLinkSendC("LOG", "0", "STREAM_ON");       // 推送类：自己指定 key
btLinkStream("LOG", line);                  // 日志流：内部 10Hz 节流 + 给响应让路
// 大块（几 KB）：StreamBegin / Write / StreamEnd，正文不进队列
```

`btLinkSend*` 只是**入队**。真正 notify 发生在 `btLinkPoll()`（loop() 里），
每轮最多 `BT_POLL_BUDGET_MS` 毫秒、片间喂一次狗。

### 固件侧：收

```cpp
void onWrite(...)  { btLinkOnWrite(bytes, len); }   // 回调里只有这一行
void loop()        { btLinkPoll(); logDumpPump(); } // 派发 + 流式回拉
```

`btLinkPoll()` → `handleCommand()`，**永远在主任务**，所以 handler 里可以
直接碰 LVGL / NVS / SPI。BLE 回调里绝不解析指令。

### 网页侧

```js
const body = await BtLink.call("MACRODUMP", "MACRODUMP:p0_M1", 800);  // 发+等
BtLink.on("LOGDUMP", body => { ... });                              // 推送
```

## ME 键文本通道（`ME_*`）

ME 键带的内容不是"按什么键"，而是**一整段要贴给主机的文本**。
中文没法用纯 ASCII 打字发出去，所以这段文本在链路上是 **hex 字符串**，
由主机端（电脑上的解码程序）按 `[HEXS]…[HEXE]` 协议还原。

### 线上协议

```
主 → 键盘   ME_START              开一段接收（截断 /me_hex.txt）
主 → 键盘   ME_DATA:<hex 片段>    追加（每片 ≤128 个 hex 字符）
主 → 键盘   ME_END[:flag]         收尾
主 → 键盘   ME_SEND               不下发文本，把**当前存着的**立刻打一遍

键盘 → 主   MEEND:<key>:OK:<落盘字节数>:<flag>     收尾回话
键盘 → 主   MESENT:<key>:OK                       ME_SEND 回话
```

**`ME_END` 的 flag**（就是"要不要立即发送"那个开关）：

| 指令 | 行为 |
|---|---|
| `ME_END` | 只存进 `/me_hex.txt`，等用户按键盘上的 ME 键 |
| `ME_END:0` | 同上（显式写 0） |
| `ME_END:1` | 存进去之后**立刻**通过 USB HID 打给主机 |

⚠ 两种模式下 `/me_hex.txt` **都会**被更新 —— 区别只是"要不要现在就打出去"。
所以「立即发送」之后**再按 ME 键**，打出来的还是同一段文本（不重复、不为空）。

⚠ **老网页发的是光秃秃的 `ME_END`**，走 `startsWith` 之后 flag 解析成 0，
行为和以前**一模一样**。所以加这个 flag 对现有网页端是零影响的，
不需要同步升级页面就能用。

⚠ flag **故意只认 `'1'`**，不做更宽松的解析：它的语义是"要不要动主机键盘"，
解析得越宽松，越容易出"用户以为没发、其实发出去了"这种反向事故。

### 为什么 flag 挂在 `ME_END` 上，而不是另发一条"现在发"的指令

「存进去」和「发出去」必须是**同一条指令**里的两个动作。分成两条就多一个
可能丢失的环节 —— 手机那边 `ME_END` 发成功了、"发"那条指令却在蓝牙断开的
瞬间丢了 → 键盘里存了，用户以为发出去了。挂在 `ME_END` 上，收尾和发送
在固件里是原子的，不存在半截状态。

`ME_SEND` 是**另一回事**：它不下发文本，只是"把现在存着的打一遍"，
等价于远程按了一下 ME 键。

### 落盘字节数就是丢片的唯一线索

固件收完会回 `OK:<落盘字节数>:<flag>`。这个字节数 = 写进 `/me_hex.txt` 的
**hex 字符数**。主机算得出自己发了多少（`2 × UTF-8 字节数`），两个数对不上
就是**传输丢片**了。

⚠ 为什么必须靠这个：固件的指令队列只有 **8 格**，满了会**丢掉最老的一条**
（`bt_link.cpp` 的 `lineSubmit()`：宁可旧指令丢，也不能让新指令进不去）。
丢掉一条 `ME_DATA` → 存进去的文本少了一段 → **固件自己不会报错**。
静默的数据损坏比报错难查得多，所以主机端一定要拿这个字节数对一下。

⚠ 因此主机端**发 `ME_DATA` 必须有节奏**（网页端和 iOS App 都是每条间隔
50ms）。一口气灌几十条会把固件的队列灌爆。

### iPhone / 手机端

⚠ **Safari（iOS / iPadOS）完全不支持 Web Bluetooth**，所以网页端那个
`s3-setting.html` 在 iPhone 上**用不了**（Chrome on iOS 也只是 WebKit 壳，
继承同一个缺口）。iPhone 上必须用原生 App —— 见 `ios/` 目录。

`ios/MX9BLE` 是协议库（纯逻辑 + CoreBluetooth，`swift test` 可测），
`ios/MESender` 是 SwiftUI App。**改协议时两边都要改**：
`src/lvgl_s3.ino`（固件）、`../s3-setting.html`（网页）、
`ios/MX9BLE/Sources/MX9BLE/MEProtocol.swift`（iOS）。

## 配置 JSON（CFG\*，schema v3）

**键盘里存的配置，收和发都走这一份 JSON。** 网页上那个"配置 JSON"文本框
是它的原文；连上蓝牙会自动拉一次，上面所有配置表单随之填成真实值。

### 线上协议

和 bt_link 是同一套链路，没有另开通道：

```
主 → 键盘   CFGBEGIN:<总字节数>        开一段接收（整份）
           CFGPATCH:<总字节数>       开一段接收（增量，见下）
           CFGDATA:<正文片段>           每片 ≤ CFG_RX_CHUNK_MAX(200) 字节
           CFGEND#<请求号>             收尾（整份）
           CFGPATCHEND#<请求号>        收尾（增量）
键盘 → 主   CFGDUMP:<请求号>:LEN:<总字节数>   长度握手（见下）
           CFGDUMP:<请求号>:<片段> ×N   正文完整
           CFGDUMP:<请求号>:END         收尾标记
           CFGSAVE:<请求号>:OK:<项数>:<毫秒>   或   ERR:<原因>
           CFGSAVE:<请求号>:OK:<项数>:<毫秒>:PARTIAL:<失败数>:<键名>
           CFGERR:<原因>                整条请求被拒（内存不够 / 链路忙 / JSON 生成失败）
```

⚠ `PARTIAL` **不是**失败：值已经写进 RAM 并提交了，键盘当场就是新的，但有
若干项**没存进 flash**，断电会丢。原因是 `Preferences::put*` 写不下新键时
**静默失败**（返回 0），而 `nvs` 分区只有 20KB 且是只增不减的日志结构。所以
这一条必须如实报出来 —— 让"保存成功"真的等于"存住了"。

### 增量：只改其中几项

网页上每个控件单独保存时走这条路，不走整份。收包流程和整份**完全一样**，
区别只在收尾时传给 `cfgApplyDoc` 的 `isPatch` 标志。

```
CFGPATCH:<总字节数>
CFGDATA:<正文片段> ×N
CFGPATCHEND#<请求号>       正文 = 整份 JSON 的一个子集
```

子集的语义**逐条与整份一致**：

| 出现的东西 | 含义 |
| --- | --- |
| `"disp_mode": 2` | 写这一个标量 |
| `"windows": { "remap": [...] }` | **整份替换** Windows 的映射（`[]` = 清空） |
| `"mac": { "macros": { "M7": "SEQ:x" } }` | 写这一个宏（`null` = 删） |
| `"gkeys": { "MAa": "SW:1+CMB:128,4" }` | 写这一个全局键（`null` = 删） |
| 没出现 | **不动** |

⚠ 增量**不带 `version`**，也**不做版本闸门**：补丁的语义本来就是"只动我点名
的那些"，老网页打过来的补丁顶多少改几项，不该整份拒掉。要对齐版本走整份那条路。

⚠ 删一个键必须显式发 `null` —— 补丁里"键不存在"的意思是**不动它**。网页那边
靠"在深拷贝上跑一遍 mutator、再和当前模型求差"来生成补丁，所以删除天然会变成
`null`。

为什么值得单开一条路：改一项（比如只切显示风格）本来要传几 KB，键盘那边收几百
毫秒，网页传完还要再整份拉回来确认一趟 —— 改成补丁后是几十字节，而且**不带
`disp_mode` 就不会挂整屏重建**。

正文里**绝对不能有 `\n` / `\r`** —— 接收侧按行攒，混进换行会被切成多条
指令，JSON 被劈成两半。网页那边用 `JSON.stringify`（不带缩进）压成一行。

⚠ `LEN:` 握手行不是可选的诊断信息，而是**协议依赖项**。正文是分片发的，而
**丢片是静默的**：一条 ATT 通知带不下就被协议栈整条丢掉（`BT_PAYLOAD_MAX`
是 20，协商失败时正好是上限），而收尾标记 END 照样会到。主机手里没有总长就
只有"看着像完整的"这一个依据，于是可能拿一份正好切在某个 `}` 上的残缺正文
去 `JSON.parse` —— 那是**语法合法但缺内容**的配置，页面照着它显示、甚至
照着它回写，把缺掉的部分清零。有了总长，主机在收到 END 时按 **UTF-8 字节数**
对一遍，对不上就明确报"传输丢片"而绝不交付。

⚠ `LEN` 与正文首片是**连在同一个 body 里**发出的，不是独立一行 —— 20 字节
预算下每片正文只有 9 字节（`chunkRoom` = 20 − 头长 10 − 1），而 `LEN:20480`
加换行要 10 字节，独立成行会把这一行从中间切开、主机再也拼不回完整的
`LEN:20480`。主机侧必须把 `LEN:356{"version":2,...` 这种粘连形态一起认掉。

### v3 的内容

```jsonc
{
  "version": 3,              // 版本闸门，不等于 3 就整份拒绝
  // 十三个标量
  "disp_mode": 0, "saver_mode": 0, "curr_prof": 0,
  "light_on": true, "brightness": 128, "effect": 0,
  "ind_level": 2, "key_fx": 0,
  "alarm_on": false, "alarm_h": 7, "alarm_m": 30,
  "sht_offset": 0.0, "set_epoch": 1730000000,

  // 方案块：按操作系统分，不再是 remap[4] + 顶层 macros
  "windows": {
    "remap":  [ {"from":224,"to":227} ],       // 定长：一个都没配就是 []
    "macros": { "M1": "SEQ:ab", "M2": "CMB:128,4" }   // 稀疏，没设的不出现
  },
  "mac": {
    "remap":  [],
    "macros": { "M7": "SEQ:1234567891" }
  },

  // 全局键留在顶层，不分系统
  "gkeys":  { "MAa": "SW:1+CMB:128,4", "MA_ph": 0, "MB_ph": 0 },

  // 倒计时：只读
  "timer":  { "run": true, "remain": 3661, "total": 3661 }
}
```

#### 方案从 4 个改成 2 个

方案这一维度不再是"四个玩法档"，而是**按操作系统分**：`windows` 和 `mac`。
`TOTAL_PROFILES` 相应地从 4 改成 2。

**NVS 键名一个都没改**：方案 0 仍然是 `p0_*` / `rmp_0_*`，方案 1 仍然是
`p1_*` / `rmp_1_*`。也就是说"方案 0 = Windows、方案 1 = macOS"只是给已有的
0/1 重新起了名字，**里面已经配好的 remap 和宏原样接着用**。p2/p3 的数据留在
NVS 里但固件不再读取（用户明确要求彻底废掉）—— 键还占着分区，但 NVS 本来
就只增不减，留着旧键并不占新键的位置。

⚠ 开机读 `curr_prof` 时**必须钳位**：NVS 里很可能还躺着旧固件写的
`curr_prof = 2` 或 `3`，不钳位就会越界去索引 `profileRemaps[2]`。已在
`setup()` 里加上并记一条告警。

`profile_icons.h` 里的四个图标本来是 win / mac / game / work，砍到 2 个之后
正好剩 win + mac，语义天然对上；`profile_icon_get()` 自带越界保护，那个头文件
不用动。

#### 宏键名：JSON 里不带系统前缀

v2 的 `"p0_M1"` 在 v3 里写成 `"M1"` —— 块名已经说明了是哪个系统，前缀是冗余的。

| JSON 键 | 所在块 | 结果 |
|---|---|---|
| `"M7"` | `windows` | 存成 `p0_M7` |
| `"M7"` | `mac` | 存成 `p1_M7` |
| `"p0_M7"` | `windows` | 放行（老 JSON 兼容），存成 `p0_M7` |
| `"p1_M7"` | `mac` | 放行，存成 `p1_M7` |
| `"p0_M7"` | `mac` | **拒绝** |

最后一条是故意的：`"p0_M7"` 出现在 `mac` 块里几乎一定是"从 Windows 那段复制
过来忘了改"。默默存成 mac 的 M7 等于"按了 M7 结果 Windows 的宏跑在了 mac 上"，
而页面上看不出任何异常 —— 那比直接报错难查一百倍。

另外**拒绝前导零**（`M01`）：它按十进制解析等于槽 1，能过范围检查，但 NVS 里
存下的键是 `p0_M01`，而 `executeMacro` 读的是 `p0_M1`，两者永远对不上，而且
那把键会留在 NVS 里删不掉。

#### 语义：四个字段的规则各不相同

| 字段 | 出现 = | 空值 = | 没出现 = |
|---|---|---|---|
| `<块>.remap` | 该系统**整份替换** | `[]` = 清空这个系统 | 这个系统不动 |
| `<块>.macros.<键>` | 写这一个宏 | `null` / `""` = 删掉它 | 这个宏不动 |
| `gkeys.<槽>` | 写这一项 | `null` / `""` = 删掉它 | 这一项不动 |
| `timer` | — | — | — |（**只读**，见下） |

- `remap` **定长**：一个规则都没有时也要发 `[]`。缺项的话"这个系统没规则"
  和"这个系统没提"分不开，而后者按本模块的规矩是"不动"，于是"清空某个系统"
  根本清不掉。
- `macros` **稀疏**：24 个键全发光键名就 200 多字节，而绝大多数人只设了三五个。
  **删掉一行 JSON 就是删掉一个宏。**
- `MA_ph` / `MB_ph` **永远发**：0 是合法值，"没这个键"和"相位是 0"必须分得开。
- `gkeys` 留顶层、不进 windows/mac：MA/MB 是"按一下换一套动作"的全局键，和
  当前跑在哪个系统没关系；拆成两套只会让 NVS 多占一倍、页面多出一倍卡片。

#### timer：进 JSON，但**只读**

`cfgBuildJson` 每次拉取时现报 `{run, remain, total}`，所以页面上看到的是键盘
此刻真在跑什么。`cfgApplyJson` 收到它会**原样忽略**：不写 NVS、不改运行状态。

这是有意的。倒计时本来就是运行内存里的一次性倒数（`TIMERSET:` 设、跑完归零、
断电归零）。落盘会带来两个坏处：断电重启后倒计时"复活"了而用户以为它已经随
断电结束；以及每次打开网页点任意一个"保存"都会把这个快照写一遍，把一个纯
运行时的量伪装成配置 —— 那比没有这个字段更容易误导。`TIMERSET:` 通道保留。

### 容量

接收缓冲不是 .bss 固定数组了，是 `ps_malloc` 的 `CFG_BUF_SIZE`(20480) × 2
（收发各一份，`setup()` 里就分配好）。方案砍到 2 个之后最坏情况降到约
**8.5KB**（24 个满宏 + 2×32 条满映射 + 满全局键），余量很宽。典型配置
几百字节、2~3 片就发完。

### 故意**不**进 JSON 的东西

| | 原因 |
|---|---|
| **ME 键文本** | 可能十几 KB 且要转 hex，本来就走的二进制通道 |
| **壁纸** | JPEG 裸字节（含 0x00），按行攒会碎成渣 |
| **日志 / 告警** | 运行时事件，不是设置 |

这三个各自保留原来的 `ME_*` / `LOGO_JPEG_*` / `LOG:*` 通道。

### 老协议还在

`REMAP:` / `SET:` / `GSET:` / `GKEYDUMP:` / `MACRODUMP:` / `REMAPREAD:` /
`GKEY_RESET:` / `MACROS_RESET:` / `REMAP_RESET:` / `DISP_MODE:` / `TIME:` /
`ALARMSET:` 这些指令**固件里仍然全部保留**，老页面/老脚本还能用。网页这边
的保存按钮已经全部改走 JSON，但删掉老指令是下一步的事（要先确认没有别的
工具在用它们）。

⚠ **remap 的写入路径两边共用 `cfgStoreRemap()`**（一个函数）。共用是故意的：
两条路必须落出完全一样的 NVS 布局，否则用户在 JSON 里改一遍、再用老协议存
一遍，两边会互相覆盖出不同结果，而现场没有任何异常。

### 踩过的坑（改协议前先读）

- **单条通知能带多少字节 = 协商后的 ATT MTU - 3。协商失败时（手机端浏览器
  常见）只有 20 字节，超出的不是被截断而是整条被协议栈丢掉。** 症状统一是
  "网页只等得到超时，然后误以为键盘里是 0 条配置"。这解释了那个一直归因错的
  不对称：1 条规则整行 20 字节能过、2 条 28 字节就丢。
  ⚠ 别用 `BLEDevice::getMTU()` 算预算：它返回 `m_localMTU`（`setMTU(517)`
  自己设的本地值），不是协商结果。
- **分片之后不能一口气同步推完。** 8KB 日志按 20 字节一片是 400+ 片，
  同步推完要把主循环按住 8 秒 —— 键盘不扫描、屏幕不刷新、按键全部失灵。
  （看门狗拆掉之前更糟：那会儿 loop() 还挂在 10 秒任务看门狗上，直接就是
  一次复位，"回拉日志把键盘搞重启"就是这么来的。现在它只是"卡住 8 秒"，
  性质完全不同 —— 前者是无声的故障，后者至少能看见界面停更。）
  所以发包摊到多次 loop 上。
- **收尾标记 `END` 那一包本身也必须装得下 20 字节。** `MACRODUMP` + 业务 key
  `p3_M12` 正好 21 字节 → 整条丢掉 → M10~M12 的宏读不回来，而且日志里什么
  异常都没有。这就是 key 必须用请求号的原因。
- **包终止符用 `\r` 不用 `\n`。** `\n` 得留给正文当数据 —— LOG 回拉整个
  就是一堆换行分隔的行，用 `\n` 收尾的话日志面板里 8KB 历史会挤成一大行。
- **必须用流式 TextDecoder（`{stream:true}`）。** 一片 20 字节，一个汉字 3
  字节，分片完全可能从汉字中间切开，非流式解码会吐一串 U+FFFD 豆腐块。
- **"正文为 0 字节"必须表达成"只有一条 END"。** 读一个空方案、读一个没设的
  宏，"读到了、确实一条都没有"是有意义的结果；沉默会被网页当成"读不到"。
- **关键响应和日志流抢同一条通道，而通知不排队。** `btLinkSend*` 入队时会开
  一小段独占窗口（`BT_CRITICAL_HOLD_MS`），期间日志流自动让路。
- 空闲兜底提交从 15ms 放宽到 **80ms**（`BT_LINE_IDLE_MS`）：Web Bluetooth 的
  `writeValue` 会按协商出来的 MTU 拆包，15ms 会在同一个 `writeValue` 的两个包
  之间误判成"这条发完了"，29 字节的 `REMAP:0:clear:224,227;227,224` 被当成
  两条命令收下 → "下发 2 条只存进 1 条"。
- **"值真的变了才做副作用"这个优化，绝不能用"再比一次当前值"来判。**
  `cfgApplyDoc` 是三遍结构：第一遍校验、第二遍赋值 + 落盘、第三遍算
  `pendMask`（决定要不要 `settimeofday` / 重建主屏 / 切方案 / 换屏保）。
  第三遍如果写成 `if (*f->var == pend[i].num) continue;`，那它比较的**已经是
  第二遍刚写进去的新值**了 —— 永远相等，于是 `pendMask` 恒为 0，**四类副作用
  一个都挂不上**。
  症状特别有欺骗性：网页回 `已保存 1 项`、NVS 里也真写进去了、`cfgModel` 也
  更新了，唯独屏幕上什么都没发生 —— "同步电脑时间"报成功但钟不跳，切显示风格
  报已更新但风格不变。
  ⚠ 更坑的是它**顺带修好了另一个 bug**：网页全量下发时"改个亮度也带着
  disp_mode"，于是每次都重建主屏（"改个亮度键盘自己跳设置页"）。副作用被整体
  掐掉，这个现象自然消失了，看起来像修好了。所以真修法是让第三遍**读第二遍记
  下来的 `pend[i].changed`**，而不是再比一遍 —— 两件事必须一起做，只做一个都会
  坏。

### 换 MTU 预算要连带改的地方

`BT_PAYLOAD_MAX`（默认 20）改大之前，先确认协商结果真的拿得到；拿不到就维持
20。要接协商值的话用 `pServer->getPeerMTU(conn_id)`，**不要**用
`BLEDevice::getMTU()`。
