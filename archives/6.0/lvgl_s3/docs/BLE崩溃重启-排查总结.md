# BLE 导致固件崩溃重启：完整排查记录（2026-10-23）

> **一句话结论：真凶是 `CORE_DEBUG_LEVEL=5`(Verbose) 下 BLE 库的日志洪水 ——
> 每个 GATT 写事件打十几行、640 片 = ~1MB 日志，灌进 115200 波特率的 CDC 要 87 秒，
> 结果日志镜像任务被堵死（CDC 从此哑掉，panic 现场唯一的出口没了）、
> CPU 被日志吃掉（BLE 协议栈饿着，连接在第 300 片左右断掉）。**
>
> **不是内存泄漏，不是 SPIFFS 满，不是 JPEGDEC 解码崩了。**
> 修复：`_debug` 环境 `CORE_DEBUG_LEVEL` 5 → 3。

---

## 1. 现象

用 `tools/send_wallpaper_raw.py` 传壁纸（240×240 RGB565 = 115200 字节，
640 片 × 180 字节）时，固件**反复崩溃重启**。

关键数字：**崩在第 300 片左右**，两次实测分别是 **54180 / 54360 字节**，
高度可复现。

同时有两个更恼人的伴生现象：
- **CDC 从二进制分片一开始就一个字都不吐**（正常应该持续输出进度日志）
- **崩溃现场抓不到**（panic 回溯是空的）

---

## 2. 排查路线（按时间顺序，含走错的路）

### 第 1 步：先怀疑内存泄漏

BLE 库每收一个写事件都要 `new` 一份 `std::string`，如果那里漏了，
症状就是「传到第 N 片突然 panic」——**堆耗尽和栈溢出在症状上很像，
但修法完全不同**。

所以在 `handleLogoChunk()` 里加了探针，每 64 片报一次内部堆剩余量：

```cpp
if ((logoRxGot % (64 * 180)) < len) {
    LOG_PORT.printf("[WALLPAPER] 收到 %u 字节，内部堆剩 %u 字节\n",
                    (unsigned)logoRxGot, (unsigned)ESP.getFreeHeap());
}
```

**实测结果：内部堆全程恒定 154580 字节，一字节都没掉。**

⇒ **堆泄漏这条被证伪。**（但这个探针本身值得留着 —— 它是以后
再遇到「第 N 片崩」时能一次证伪的直接证据。）

### 第 2 步：怀疑 SPIFFS 分区满了

查开机日志里分区占用那行：

```
[SPIFFS] 总 1438481 字节，已用 159134 字节，剩 1279347 字节
```

⇒ **分区空得不能再空，115KB 存下去毫无压力。分区满这条也被证伪。**

（顺带修正一个更早的错误结论：以为「SPIFFS 单文件不能超过 4096」是
`/logo.bin` 存不下的原因。真实情况是单文件确实不能超一个 block，
所以改成了分片存 `/logo000.bin`…`/logo056.bin` + `/logo.ok` 标记；
但分区容量本身从来不是瓶颈。）

### 第 3 步：怀疑 JPEGDEC 解码崩了

之前有另一个独立问题确实栽在 JPEGDEC 上（PSRAM 上的输入缓冲被直接
交给 JPEGDEC 解析，见 memory 里那条）。但**这次的崩溃发生在 RAW 通路**，
板子上根本没跑 JPEGDEC。

⇒ 与本次无关，排除。

### 第 4 步：装黑匣子，别猜了

用户明确要求「你不用猜吧」—— 于是做了**黑匣子**（`src/panic_trace.h`）：

1. `ets_install_putc2(romPutc)` —— 接管 ROM 的 putchar，IDF 的日志 /
   assert / panic 回溯全进一块 8KB 内存环
2. `g_panic_abort = panicHook` —— panic 发生时把环的尾巴抄进 **RTC 慢存**
   （跨复位不丢）
3. 开机时把这段文字打进日志；另有 **`PANIC` 命令**直接从慢存回传现场，
   **什么时候问都问得到**（不必赌「开机日志还没被新日志顶掉」）

**黑匣子第一次就白折腾了一轮** —— 那段 `[PANIC]` 打印被放在
BLE 日志环缓冲**分配之前**，所以 `LOG:dump` 根本拉不到，现场只进了
UART0 和 CDC。

⇒ **打印 panic 现场的位置必须在 BLE 日志环分配之后。**
（这条和「日志环在 PSRAM 上、重启不清零」一起，记在 README 的
「怎么让板子重启」小节里。）

### 第 5 步：抓到了真凶

黑匣子装好后，崩溃现场里赫然是 **BLE 库自己的 verbose 日志**：

```
ESP_GATTS_WRITE_EVT
setValue(...)
[xSemaphoreTake] ... / [xSemaphoreGive] ...
```

**每个 GATT 写事件十几行。** 640 个写事件 ⇒ **~1MB 日志**。

算一下就知道为什么完蛋：往 115200 波特率的 USB CDC 灌 1MB 需要
**87 秒**，而 USB 口只有一个 ——

- **日志镜像任务被彻底堵死** ⇒ CDC 从二进制分片开始就一个字都不吐
  （panic 现场唯一的出口没了，所以前几轮怎么都抓不到现场）
- **CPU 被日志吃掉** ⇒ BLE 协议栈饿着 ⇒ **连接在第 300 片左右断开/崩溃**
  （这就是那个「稳定复现在第 300 片」的原因）

⇒ **修复：`_debug` 环境的 `CORE_DEBUG_LEVEL` 5(Verbose) → 3(Info)。**

修复后实测：**115200/115200 字节零丢包，640 片全收齐**。

## 3. 顺带修掉的三个坑

### 坑 1：`Serial.setDebugOutput(true)` 会把 CDC 整个打死

它的内部实现是 `ets_install_putc2(cdc0_write_char)` —— 把 ROM 的 putchar
直接接到 **TinyUSB 的 CDC TX FIFO**，而**那个 FIFO 不是线程安全的**。

蓝牙协议栈的 `log_d()` 和主循环的日志镜像任务会并发写它 ⇒
症状是「CDC 通道整个死掉」。

⇒ **固件现在改成：先进自己的内存环，再由日志镜像任务统一搬进 CDC/UART0。**
（见 `src/panic_trace.h`）**`Serial.setDebugOutput(true)` 禁用。**

### 坑 2：panic 现场打印得太早

见上面第 4 步。位置必须在 BLE 日志环缓冲分配之后。

### 坑 3：主机「传输途中问固件收到多少了」这个动作本身会出事

主机每传 64 片问一次 `LOGO_STATUS`，这个**文本命令插在二进制流中间**。

实测三次崩溃分别发生在第 **121 / 621 / 121** 片，而探测点在第
**128 / 640 / 128** 片 —— **每次都紧贴在下一次探测之前**。

⇒ **传输时默认加 `--no-probe`**；固件回报的 `LOGO_STATUS` 只在传输前后问一次。

（注意：最终确认的真凶是日志洪水，探测本身不是根因。但**在日志洪水的
环境下**，往已经在喘气的链路上再插文本命令，确实会把崩溃提前。）
`--no-probe` 保留下来作为稳妥做法。

## 5. 留下的规矩

1. **传输壁纸时 `CORE_DEBUG_LEVEL` 必须是 3。**
   要查 BLE 栈细节时临时改回 5 重新编译，**但传输壁纸时务必是 3。**

2. **别用「症状像」代替证据。**
   「堆耗尽」和「栈溢出」症状很像，「日志堵死」和「内存不足」也很像。
   每个假设都要配一个**能一次证伪的探针**（本轮是：堆剩余量探针 →
   证伪泄漏；分区占用那行 → 证伪分区满；黑匣子 → 直接看到日志洪水）。

3. **panic 现场要存在芯片里，不能只靠日志。**
   日志环只有 8KB，跑一会儿就被顶掉了。`PANIC` 命令读 RTC 慢存，
   **什么时候问都问得到**。

4. **黑匣子只在 debug 构建生效**（`LOG_CDC_MIRROR` 圈定），
   产品固件不白占那 10KB。产品固件要抓现场走 UART0（接 USB-TTL）。

5. **BLE 命令集里没有 `REBOOT`** —— 它只挂在 UART0 的 `handleUartCommand`
   上。从 BLE 复位要走 **`BOOTAPP`**。做回归验证时：
   `LOG:clear` → `BOOTAPP` → 等 20 秒 → 重连 → `LOG:dump`。
   （`LOG:clear` 不能省：日志环在 PSRAM 上，重启不清零。）
